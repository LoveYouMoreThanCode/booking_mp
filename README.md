## 三、客人下单的路径

客人这边是**两个页面**，不是一个页面加弹层：

| 页面 | 干什么 |
|---|---|
| `pages/booking/booking` | 选日期、点格子、看底栏合计，点「提交预约」 |
| `pages/contact/contact` | 核对时段清单、填手机号/称呼/备注、确认提交 |

两页之间用 `getApp().globalData.pending` 传选择——选中的格子可能有几十个，
塞进 URL 不现实。

**为什么非要拆成两个页面**：一开始「填联系方式」是贴底的弹层，
真机上输入手机号时字打进去了却不显示，收起键盘才出来，备注框还会被键盘盖住。
根因是「`position: fixed` 贴底弹层 + 原生输入控件」这个组合——
弹层高度靠键盘高度算，输入框又是原生层，两边对不上。
搬到独立页面后输入框回到普通文档流，不 fixed、不套 `scroll-view`、
用系统默认的键盘避让，这一整类问题就不存在了。

搬到独立页面后**备注框好了，两个 `<input>` 还是瞎的**——这一步才把差别分出来：
同一台手机、同一页、同样的样式，`<textarea>` 全程正常，`<input>` 打进去的字
压根不显示（输入过程中看不见，**收起键盘也追不回来**），而 `bindinput` 是好的
（值拿得到，只是框自己不渲染）。

试过按文档加 `always-embed="{{true}}"`（强制同层渲染），**结果更糟**：连
「收键盘后能显示」都没了。所以那个属性不要加。

最终的处置是**不查 `<input>` 为什么坏，直接不用它**：填写页三个框
（手机号 / 称呼 / 备注）统一成同一个 `<textarea class="textarea">`，
处理方式也完全一致——打字时只往页面实例上存一个字，不 `setData`、不校验、不数字数。
手机号的合法性挪到点「确认提交」时才判，不合格就提示一句让他接着改。

`test/smoke.js` 末尾有一组静态断言盯着这件事（填写页不许出现 `<input>`、
不许有 `always-embed`、不许绑 `value`、三个框必须同一个 class）——
删掉它们不会让任何一条功能断言变红，只会让真机上的输入框重新变瞎。

**代价**：手机号失去数字键盘（`type="number"` 是 `<input>` 才有的）。
提交时会 `replace(/\D/g,'')` 兜住，所以只是要多按一下切键盘，不影响正确性。

`pages/pricing/pricing.wxml` 里还剩**最后一个 `<input>`**（老板填价格那个）。
它暂时没换，因为快捷价签要能把价格写进框里、离不开 `value` 绑定，
而「受控的 textarea」还没在真机上验过。如果老板反馈那里也看不见，就换掉它。

## 四、管理入口

在预约页**长按标题「羽毛球场地预约」**→ 输入口令 `8888` → 进预约管理页。

管理页有两块：

- **预约管理**（默认）：待确认 / 已确认 / 已取消三个分页。
  点卡片看详情，点「确认」标记已谈妥，点「拨号」直接打给客人。
- **改价格**：右上角「改价格」进价格页。

### 价格页怎么用

格子 = 场地 × 一小时，**和客人页的格子一模一样**。填 90，这一小时就是 90，
客人那一格看到的也是 90。

| 操作 | 效果 |
|---|---|
| 点单个格子 | 选中 / 取消 |
| 点**场地名**（表头蓝字） | 整列全选 / 全不选 |
| 点**时间**（左侧） | 整行（这一小时 × 全部场地）全选 / 全不选 |
| 填价格 → 「应用到选中」 | 覆盖选中格子的价格 |
| 填价格 → 点 `¥60`/`¥90`/`¥100` 小标签 | 快速填入 |
| 「恢复规则价」 | 删掉手改的值，回到按星期/时段自动算的价格 |

橙色格子 = 被手改过。

**改价只影响之后的新预约**。已经提交的订单里存的是下单当时的**价格快照**，
事后改价不会回头改动它们——这是故意的，否则改一次价会把历史订单的对账全部搞乱。

## 五、现在的限制（重要）

### ⚠️ 口令现在是**真的**安全边界了，而它还是那个 `8888`

接云之前，口令被猜到的后果只是「店员误点了几下」——数据本来就在各自手机上。
**现在不是了**：库里是真实客人的姓名和手机号，而管理接口在云上。

`8888` 写在 `core.js` 里，反编译可见。谁拿到它，就能直接调 `getSchedule`
把**全部订单和手机号**拉走，或者调 `clearAll` 把库抹掉。

这是明确接受的取舍（先跑通闭环），代价说清楚。补上只要一步：

```js
// cloudfunctions/updateBooking/index.js、savePrices/index.js、clearAll/index.js
const ADMIN_WHITELIST = [];   // ← 填上老板的 openid
```

填了之后口令那条路就**完全**不走了（白名单优先）。`getSchedule` 里也有一处
同样的常量，四个文件都要填。openid 从哪来：云函数日志里打一次
`cloud.getWXContext().OPENID`，或者用云开发控制台的「用户管理」。

`smoke.js` 里有一条断言把三个文件里那块鉴权代码**逐字比对**（它们是复制粘贴的，
云函数之间没法共享代码）—— 改一处漏两处会立刻红。另外还有一条静态断言盯着
云函数不许读 `event.admin`：身份只能由云函数自己从 `OPENID` 算出来，
不能由调用方自报。

### ⚠️ 收尾时要删掉的东西（别带进正式版）

- **控制台里手工插的那条测试单**（`bookings` 里 2026-09-19 那条）—— 它是搭起来
  时用来验「客人页读的是云端真实占用」的，没有 `phone`/`items`/`total`，
  不是一笔真订单。订单页能把它画出来（缺的字段会退化成空），但别留着。
- **临时诊断**：`getSchedule` 里的 `anyBookings` / `shape`、`store.js` 的
  `fetchAll` 和 `core.js` 的 `refresh` 里那几行 `console.info`。它们是为了定位
  「界面一片空」而加的（那一类问题里「没回来」和「回来了但日期对不上」
  长得一模一样）。第 3 步统一删。
- `cloudfunctions/concurrencyCheck/` —— 体检函数本体。**云上那份已经删了**
  （它没有任何鉴权，留在公网上就是个能写库的接口）。本地台架留着。

### ⚠️ 全新安装打开是空表格

**不会**再自动灌演示订单了（原来 `app.js` 的 `onLaunch` 会灌 13 条假订单）。

删掉的原因是接云之后它从「看不见」变成「有害」：防重复靠的是一个按**设备**的
标记，而云上的数据库是所有人共用的 —— 那个标记不存在，于是**每个新客人第一次
打开小程序都会往库里灌 13 条假订单**。这一行还零测试覆盖：`smoke.js` 从来不加载
`app.js`（它自己起了个 `App` 桩件），本地跑再多遍也绿。

代价说清楚：**新装的 App 打开是空表格**，没有假名字可以看效果。要看就自己点几单。
上线前也正好用订单页走一遍「客人提交 → 老板确认 → 拨号」。

那 13 条数据没丢，搬去了 `test/smoke.js` 当 fixture（测试需要一张有数据的表格
来验状态分布）。

价格页右上角「清空数据」**保留**了 —— 它只删不增，在云端无害，上线前清测试单要用它。

`smoke.js` 末尾有两条静态断言盯着这件事：`app.js` 里不许出现那个函数名，
也不许出现 `SEED_FLAG`。删掉它们不会有任何功能断言变红，只会让假订单重新爬回云上。

## 六、云开发：现在的结构

要花的钱：正式发布后基础套餐 ¥19.9/月；发布前免费额度够用。

**数据现在在云上**，所有人共用一份。客人手机上的订单，老板手机上立刻能看到。

### 三张集合

| 集合 | `_id` 长什么样 | 存什么 |
|---|---|---|
| `bookings` | 订单号 `Bxxxxxxx` | 订单全文：时段、价格快照、手机号、姓名、备注、状态 |
| `occupancy` | `2026-09-17\|0`（日期+场地号） | `{ slots: { "1140": "Bxxx" } }`，分钟 → 订单号 |
| `prices` | `2026-09-17\|0\|1140` | `{ dateKey, price }`，**一手改一格一条** |

三张都该设成**仅管理端可读写**：客户端一律不直连数据库，全部走云函数。
（换白名单那天不用再迁权限。）

### 五个云函数

| 云函数 | 对应 `store.js` 的 | 干什么 |
|---|---|---|
| `getSchedule` | `fetchAll` | 收 7 个 dateKey + 口令，**自己算 isAdmin**。管理员拿完整订单，否则只拿 `{dateKey, slotKeys, status}` 投影 |
| `createBooking` | `insert` | 确保占用文档存在 → 带自写重试环的事务：读占用 → 算可用子集 → 写占用 + 建订单 |
| `updateBooking` | `update` | 事务内改状态 + 同步占用表（取消即释放）。**「恢复」的占用检查也在这里** |
| `savePrices` | `savePrices` | 按格子 key 逐个写/删，写集只含被改的格子 |
| `clearAll` | `clearAll` | 清空三张集合，顺序写死：`occupancy → bookings → prices` |

**手机号没有离开过云函数。** 「客人拿不到别人的手机号」这件事由 `getSchedule`
返回什么决定（投影），不是由表结构决定 —— 所以那一层防护是真的，而不是看起来像。

### 「一格一单」是怎么保证的

云开发的数据库事务只提供**快照隔离**，官方明确说挡不住写偏（write skew）；
而且事务里**不能写 `where` 查询**，只能按 `doc(id)` 单条操作。所以
「先查一下这格有没有被占，没有就写」在云端是挡不住两个人同时下单的。

起作用的是一条容易被忽略的性质：**读不加锁，只有写才加锁。** 关键在于两次写入
**落在同一个物理文档上** —— 同一格 = 同一个 `(dateKey, ci)` 占用文档 =
两个事务写同一个**已存在**的文档 → 写冲突。这绕开了「写偏挡不住」那条限制：
冲突落在物理文档上，而不是落在一个逻辑条件上。

> **已实测**（2026-09-18，台架 `dev/concurrency-check/`，8 并发）：
> 写冲突真的会发生；**`runTransaction` 不自动重试**（冲突直接抛给调用方），
> 所以 `createBooking` / `updateBooking` 里的重试环是**必须的，不是保险**。
> 补上环之后 8 并发是 1 成功 / 7 被拒 / 0 抛错。
>
> ⚠️ 判冲突**不能看 `errCode`**（同一个 `-1` 也出现在「文档不存在」等处），
> 只能看文本里的 `TransactionConflict`。官方改文案时重试环会直接抛出，
> 不会悄悄少重试 —— 响亮地坏。

**代价**：一个场地一天只有一个锁，所以同场地同一天的下单会串行。4 片场地、
熟客为主的量级下不会撞到（实测重试一次就够）。

### ⚠️ 云函数跑在 UTC，不是北京时间

已实测 `tzOffsetMinutes: 0`。所以**云函数里任何取「今天」的地方都必须显式按 +8 算**。
现在的做法是绕开它：`dateKey` 一律由客户端算好传来，云函数只做「是不是在我认可的
窗口内」的形状校验。北京时间 0 点到 8 点之间是这件事最容易发作的时段 ——
而那正是客人订当晚场地的时段。

### 「一定要手动做」的那几件事（记录，别漏）

1. 开发者工具点「云开发」→ 开通 → 新建环境（本项目的 envId：`cloud1-d9g6qqofq25c8cc12`）
2. **等约 10 分钟** —— AppID 首次开通后云 API 要过一会儿才生效，
   立刻用会报 `cloud init error: invalid scope`
3. 控制台里**手动建三张集合**：`bookings`、`occupancy`、`prices`
   （自动建集合的功能已经被官方移除了）
4. 每张集合的「权限设置」改成**仅管理端可读写**
5. 按**仓库根目录**导入工程（不是 `miniprogram/`），云函数才认得到
6. 部署云函数。命令行：

   ```bash
   CLI=/Applications/wechatwebdevtools.app/Contents/MacOS/cli
   "$CLI" cloud functions deploy --env cloud1-d9g6qqofq25c8cc12 \
     --names createBooking --project <仓库根> -r
   ```

   ⚠️ **新函数第一次部署一定会报「当前函数处于 Creating 状态」** ——
   它在后台建函数实例。**等 30 秒重试一次就好**，不是配置错了。

### 本地测不了的、只能真机验的

云函数里的逻辑**在本地测不到**（`wx-server-sdk` 跑不起来，jsc 里也没有云数据库）。
三个台架（`dev/get-schedule/`、`dev/booking-tx/`、`dev/concurrency-check/`）
能在花掉一次真机往返之前把函数里的分支走一遍，但**查询语义、事务加锁、
`OPENID` 从哪来**这些只能上云量。别把台架全绿当成验收通过。

真机验收清单：

1. **闭环**：A 手机（客人）下单 → B 手机（老板）**立刻看到这一单**
2. **并发**：8 个并发下同一格，只能成 1 单（第 0 步已验过最小复现；
   第 2 步做完要再验一次**真的 `createBooking`** —— 它比最小复现多了订单写入、
   价格快照、`skipped` 子集计算，事务里的操作数不一样）
3. **改价**：老板改一格价格 → 客人页那一格跟着变
4. **取消释放**：老板取消一单 → 那一格在客人页重新变空
5. **恢复撞车**：老板 A 取消一单、老板 B 在另一台机上把那些格子订走，
   然后 A 点「恢复」→ 必须**被拒**（而不是造出两单占同一格）
6. **重开**：杀掉小程序重开 → 第一屏立刻有内容（本地镜像），随后刷新成权威值
7. **断网**：飞行模式下改价/确认 → 弹失败提示，界面回滚成原样（不是假装成功）

第 5 条是这个设计里最要紧的一条：它是「客户端查缓存」换成「服务端事务」的**唯一**
理由，而本地测不出来（本地后端没有事务）。

### 还没做的

- **订阅消息通知**（客人提交后给老板推一条）。个人主体只能用**一次性订阅**，
  一次授权一次推送。
- **恶意预定防御** / 配额 / 黑名单 —— 明确不在范围内。`createBooking` 谁都能调，
  因为客人下单本来就不该要身份；它能校验的只有形状（订单号合法、日期像日期、
  格子数不越界、手机号是字符串）。
- **占用表的对账 / 自愈**：订单的 `slotKeys` 和占用文档是同一事实的两份拷贝，
  事务保证它们不会各写各的。但如果有人在控制台手改数据造成漂移，
  现在**没有工具能发现** —— 记在这里，不假装它不存在。

## 七、改配置

都在 `miniprogram/utils/core.js` 顶部的 `CONFIG`：

```js

openHour:   8,      // 营业开始
closeHour:  22,     // 营业结束

slotMin:    60,     // 计价粒度：价格每小时可以不同
bookMin:    60,     // 预定粒度：客人最少订 1 小时

daysAhead:  7,      // 可预约未来几天
nightStart: 18,     // 晚间时段从几点开始

rates: {
  weekdayDay:   60,   // 工作日白天（元/小时）
  weekdayNight: 90,   // 工作日晚上
  weekend:      100,  // 周末整天
},
```

### 两个粒度现在是同一个

- **`slotMin`（计价）** —— 价格按小时算，改价页一行就是一小时。
- **`bookMin`（预定）** —— 客人界面上一格也是一小时。

**改价页和客人页的格子完全对应**：你在改价页把 18:00 填成 ¥99，
客人那一格看到的就是 ¥99，下单也是 ¥99。

> 这两个值**必须一起改**。`slotMin` 从 30 调到 60 时，`rates` 也得跟着翻倍——
> 否则客人看到的价格会整体打对折。从半小时粒度改过来时还要**换一个存储键**
> （见 `utils/store.js` 的 `PRICE_KEY`），不然老板按半小时改过的价
> 会被当成小时价读出来，静默少收一半钱。

> `prototype/core.js` 里的这份配置**已经过时**了（见文末「关于原型」）。

## 八、跑测试

```bash
./test/run.sh                  # 小程序端：306 项断言
./dev/get-schedule/run.sh      # getSchedule 云函数：46 项
./dev/booking-tx/run.sh        # createBooking / updateBooking / clearAll：106 项
./dev/concurrency-check/run.sh # 并发地基的体检：31 项
```

全部不需要 node，也不需要开发者工具 —— 用 macOS 自带的 `jsc`，
`test/smoke.js` 用桩件模拟 `wx` API，把四个页面的 `Page` 对象真跑一遍
（连 `setData` 的路径写法都模拟了），覆盖下单、冲突剔除、价格快照、改价、
状态流转、两段式渲染、全新安装、落库失败回滚、云端后端的调用名与参数、
外部数据的形状护栏等。

⚠️ **三个 `dev/` 台架的成败是印在输出里的，不体现在退出码上**（jsc 里未处理的
Promise 拒绝是静默 exit 0）。看最后那行「通过 N / 失败 M」。
`test/run.sh` 有退出码，失败是 exit 3。

其中最后一组是**静态检查**：直接读源码文本，确认填写页没有 `<input>`、三个框都是
同一个 `class="textarea"`、没有 `value` 绑定、`app.js` 里没有自动灌演示数据、
`store.js` 的后端开关指向 `cloudBackend`、云函数不读 `event.admin`、
三个云函数里的鉴权代码逐字相同。

这类约定桩件测不出后果，但没有断言盯着就一定会被后人当冗余删掉 —— 它们**一条都
不会**让别的断言变红，只是在真机上（或接云之后）才发作：

- 输入框那几条：真机上打进去的字不显示
- `app.js` 那两条：`smoke.js` 从不加载 `app.js`，所以本地跑一万遍也绿，
  而每个新客人第一次打开都会往共享数据库里灌 13 条假订单
- `const backend = cloudBackend` 那条：改回 `localBackend` 会让整个项目
  **静默退回单机版** —— 功能看着一切正常，只是客人的订单老板永远收不到。
  上面几百条行为断言一条都发现不了它（它们测的是两个后端各自好不好使，
  不是出货用的是哪个）

### ⚠️ 改代码前必须知道的：写操作是异步的

数据读写都在 `utils/store.js` 里，后端可换（现在是 `cloudBackend`，
测试里靠 `_useBackend()` 切回 `localBackend`）。

**每个读写都返回一个 task**，有 `.done(fn)` / `.fail(fn)`：

- **本地后端在 `.done()` 注册的那一刻【同步】回调**——数据本来就在手边
- 云端后端**异步**回调——网络回来才 settle

所以「拿到数据之后要做的事」**必须写在 `done` 里**：

```js
对的：  core.refresh(() => this.repaint());
错的：  core.refresh();
        this.repaint();     // 本地能跑，云端必崩，而且本地测不出来
```

写操作同理：`core.createBooking(...)` 返回 task，`.done(res)` 里才是
`{ ok, booking, skipped }`；`.fail` 是落库失败。**写失败必须让用户看得见**——
客人不能看到「已提交」而什么都没落库，老板不能看到卡片变成「已确认」而云端没改。
内存里的乐观改动会自动回滚，但提示要页面自己给。

### 页面统一是「两段式」

三个有数据的页面（预约 / 订单 / 改价）都是同一个形状：

| | 干什么 | 取数吗 |
|---|---|---|
| `repaint()` | 把手上这份缓存画上屏 | **不取** |
| `refresh(cb)` | 取一次权威数据，**回来之后**再 repaint | 取 |
| `onShow()` | `this.repaint(); this.refresh();` | |

这么分是**为了现在**：数据在网络上，回来得晚。先 repaint，界面立刻有内容
（冷启动第一屏就靠这个），代价是第一屏可能旧一拍。

**凡是依赖最新占用情况的判断，都必须写在 `refresh` 的 `done` 里。** 现在有两处：
`pruneSel()`（把被订走的格子从选择里剔掉）和「今天已过完时跳到最近一个可约日期」。
写在 `core.refresh()` 的下一行，本地照样全绿、云端拿旧数据算。

这不是纸上谈兵，是实测出来的：把 `pruneSel()` 挪到 `done` 外面，只有**一条**断言变红
（`sel.size` 该 0 实际 1）。格子本身反而看不出来——`repaint` 读的是实时数据，会自己
纠正过来。所以线上会看到「格子已经变成『待』了，底栏却还算着它」，客人点提交才发现被剔掉。

订单页还有一条：下拉的转圈要在 `refresh(cb)` 的**回调里**才 `stopPullDownRefresh()`。
立刻停的话，云端转圈先消失、列表后刷新，老板看到的是「下拉了、没反应」。

`smoke.js` 里有一节专门测这个（`holdServer()`）：把「服务器」按住不返回，
先断言界面已经有内容、且**没有**提前剔选择；再放行，断言剔干净了。
整套测试里只有那一节能区分「取数前」和「取数后」——其余用例跑在同步后端上，
两个瞬间是同一个瞬间。

**测试全程是同步跑的**，靠的就是「本地后端同步回调」这条性质。
`smoke.js` 里有一条断言专门盯着它：谁把本地后端改成 `setTimeout` 式，
那条会立刻红在 exit 3，而不是让几百条断言悄悄变成假绿。

> **不要在这个项目里引入 `async` / `await` 或 Promise 来做这些事。**
> 测试跑在 macOS 自带的 `jsc` 上，未处理的 Promise 拒绝在那里是
> **静默 exit 0**——断言失败会变成「假装通过」。task 没有这个问题：
> 失败仍然是同步抛出，仍然是 exit 3。

有一套桩件替掉了 `Date` 和 `setTimeout`，让「现在是几点」和
「延迟的那一下什么时候执行」都变成测试里可以拨的旋钮。

改了 `core.js` 或页面逻辑后跑一下，比在模拟器里手点快得多。
尤其是价格和占用这两块——它们出问题时在界面上往往看不出来。

测试里有一组**可控时钟**的用例（`setClock(20, 15)`），
能把「现在是几点」拨到任意时刻再跑一遍，覆盖「晚上打开」
「今天已过完」这类只有特定时间才出现的场景。

## 九、关于原型

`prototype/` 是最早用来对需求的 HTML 原型，**已经停止维护**，
和现在的小程序对不上了（它还是半小时一格、还没有过期提示）。

留着是为了回头看当初的设计取舍。**改代码请只改 `miniprogram/`**，
别拿 `prototype/` 当参考——它不反映现在的行为。

不需要了可以直接删掉整个 `prototype/` 目录。
