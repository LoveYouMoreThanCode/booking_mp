## 三、客人下单的路径

客人这边是**两个页面**，不是一个页面加弹层：

| 页面 | 干什么 |
|---|---|
| `pages/booking/booking` | 选日期、点格子、看底栏合计，点「提交预约」 |
| `pages/contact/contact` | 核对时段清单、填手机号/称呼/备注、确认提交 |

两页之间用 `getApp().globalData.pending` 传选择——选中的格子可能有几十个，
塞进 URL 不现实。

**为什么非要拆成两个页面**：一开始「填联系方式」是贴底的弹层，
真机上输入手机号时字打进去了却不显示，收起键盘才出来，备注框还会被键盘盖住。
根因是「`position: fixed` 贴底弹层 + 原生输入控件」这个组合——
弹层高度靠键盘高度算，输入框又是原生层，两边对不上。
搬到独立页面后输入框回到普通文档流，不 fixed、不套 `scroll-view`、
用系统默认的键盘避让，这一整类问题就不存在了。

搬到独立页面后**备注框好了，两个 `<input>` 还是瞎的**——这一步才把差别分出来：
同一台手机、同一页、同样的样式，`<textarea>` 全程正常，`<input>` 打进去的字
压根不显示（输入过程中看不见，**收起键盘也追不回来**），而 `bindinput` 是好的
（值拿得到，只是框自己不渲染）。

试过按文档加 `always-embed="{{true}}"`（强制同层渲染），**结果更糟**：连
「收键盘后能显示」都没了。所以那个属性不要加。

最终的处置是**不查 `<input>` 为什么坏，直接不用它**：填写页三个框
（手机号 / 称呼 / 备注）统一成同一个 `<textarea class="textarea">`，
处理方式也完全一致——打字时只往页面实例上存一个字，不 `setData`、不校验、不数字数。
手机号的合法性挪到点「确认提交」时才判，不合格就提示一句让他接着改。

`test/smoke.js` 末尾有一组静态断言盯着这件事（填写页不许出现 `<input>`、
不许有 `always-embed`、不许绑 `value`、三个框必须同一个 class）——
删掉它们不会让任何一条功能断言变红，只会让真机上的输入框重新变瞎。

**代价**：手机号失去数字键盘（`type="number"` 是 `<input>` 才有的）。
提交时会 `replace(/\D/g,'')` 兜住，所以只是要多按一下切键盘，不影响正确性。

`pages/pricing/pricing.wxml` 里还剩**最后一个 `<input>`**（老板填价格那个）。
它暂时没换，因为快捷价签要能把价格写进框里、离不开 `value` 绑定，
而「受控的 textarea」还没在真机上验过。如果老板反馈那里也看不见，就换掉它。

## 四、管理入口

在预约页**长按标题「羽毛球场地预约」**→ 输入口令 `8888` → 进预约管理页。

管理页有两块：

- **预约管理**（默认）：待确认 / 已确认 / 已取消三个分页。
  点卡片看详情，点「确认」标记已谈妥，点「拨号」直接打给客人。
- **改价格**：右上角「改价格」进价格页。

### 价格页怎么用

格子 = 场地 × 一小时，**和客人页的格子一模一样**。填 90，这一小时就是 90，
客人那一格看到的也是 90。

| 操作 | 效果 |
|---|---|
| 点单个格子 | 选中 / 取消 |
| 点**场地名**（表头蓝字） | 整列全选 / 全不选 |
| 点**时间**（左侧） | 整行（这一小时 × 全部场地）全选 / 全不选 |
| 填价格 → 「应用到选中」 | 覆盖选中格子的价格 |
| 填价格 → 点 `¥60`/`¥90`/`¥100` 小标签 | 快速填入 |
| 「恢复规则价」 | 删掉手改的值，回到按星期/时段自动算的价格 |

橙色格子 = 被手改过。

**改价只影响之后的新预约**。已经提交的订单里存的是下单当时的**价格快照**，
事后改价不会回头改动它们——这是故意的，否则改一次价会把历史订单的对账全部搞乱。

## 五、现在的限制（重要）

### ⚠️ 数据存在各人手机本地，客人和店员的数据**不通**

存储全在 `utils/store.js` 里，**现在用的是本地 storage，数据只在这台设备上**。
所以现在：

- 店员手机上看到的订单，是店员手机上自己产生的（现在是演示数据）
- 客人手机上提交的订单，店员手机上**收不到**

**自测可以，接真客人不行。** 要跑通「客人提交 → 老板收到」，
必须接微信云开发，见下一节。

### ⚠️ 管理口令不是安全边界

`8888` 写在客户端代码里，任何人反编译都能看到。体验版阶段它只用于
**防误触**（免得店员乱点改价）。正式版必须换成 openid 白名单 + 云函数校验。

### ⚠️ 演示数据

首次启动会灌 13 条假订单（张伟、李娜等），方便看界面。
价格页右上角「清空数据」可以全部清掉。

## 六、接云开发（跑通双角色）

要花的钱：正式发布后基础套餐 ¥19.9/月；发布前免费额度够用。

改造点集中在 `utils/core.js` 的存储层，业务逻辑一行不用动：

| 现在 | 改成 |
|---|---|
| `readStore()` / `writeStore()` | `db.collection('bookings').get()` / `.add()` |
| `PRICE_OVERRIDES` 内存对象 | 一张 `prices` 集合，或一个 `day_prices` 文档 |
| `createBooking` 里的占用检查 | 数据库**唯一索引**（`dateKey + court + min`），冲突时写入失败 |
| 管理口令 | 云函数里比对 `wxContext.OPENID` 是否在白名单 |
| 客人提交后的通知 | 订阅消息（个人主体只能用**一次性订阅**，一次授权一次推送） |

唯一索引这条最关键：现在的占用检查是「先查再写」，两个人同时提交有极小的
概率撞车。数据库唯一索引能从根本上杜绝，这是前端做不到的。

## 七、改配置

都在 `miniprogram/utils/core.js` 顶部的 `CONFIG`：

```js
courts:     ['1号场', '2号场', '3号场', '4号场'],  // 加场地就在这加
openHour:   8,      // 营业开始
closeHour:  22,     // 营业结束

slotMin:    60,     // 计价粒度：价格每小时可以不同
bookMin:    60,     // 预定粒度：客人最少订 1 小时

daysAhead:  7,      // 可预约未来几天
nightStart: 18,     // 晚间时段从几点开始

rates: {
  weekdayDay:   60,   // 工作日白天（元/小时）
  weekdayNight: 90,   // 工作日晚上
  weekend:      100,  // 周末整天
},
```

### 两个粒度现在是同一个

- **`slotMin`（计价）** —— 价格按小时算，改价页一行就是一小时。
- **`bookMin`（预定）** —— 客人界面上一格也是一小时。

**改价页和客人页的格子完全对应**：你在改价页把 18:00 填成 ¥99，
客人那一格看到的就是 ¥99，下单也是 ¥99。

> 这两个值**必须一起改**。`slotMin` 从 30 调到 60 时，`rates` 也得跟着翻倍——
> 否则客人看到的价格会整体打对折。从半小时粒度改过来时还要**换一个存储键**
> （见 `utils/store.js` 的 `PRICE_KEY`），不然老板按半小时改过的价
> 会被当成小时价读出来，静默少收一半钱。

> `prototype/core.js` 里的这份配置**已经过时**了（见文末「关于原型」）。

## 八、跑测试

```bash
./test/run.sh
```

不需要 node，也不需要开发者工具——`test/smoke.js` 用桩件模拟 `wx` API，
把四个页面的 `Page` 对象真跑一遍（连 `setData` 的路径写法都模拟了），
覆盖下单、冲突剔除、价格快照、改价、状态流转、两段式渲染、落库失败回滚等 **228 项断言**。

其中最后一组是**静态检查**：直接读 `.wxml` 源码，确认填写页没有 `<input>`、
三个框都是同一个 `class="textarea"`、没有 `value` 绑定。这类约定桩件测不出后果
（真机上才发作），但没有断言盯着就一定会被后人当冗余删掉。

### ⚠️ 改代码前必须知道的：写操作是异步的

数据读写都在 `utils/store.js` 里，后端可换（现在是本地 storage，
将来换成云开发只改那个文件里的一行）。

**每个读写都返回一个 task**，有 `.done(fn)` / `.fail(fn)`：

- **本地后端在 `.done()` 注册的那一刻【同步】回调**——数据本来就在手边
- 云端后端**异步**回调——网络回来才 settle

所以「拿到数据之后要做的事」**必须写在 `done` 里**：

```js
对的：  core.refresh(() => this.repaint());
错的：  core.refresh();
        this.repaint();     // 本地能跑，云端必崩，而且本地测不出来
```

写操作同理：`core.createBooking(...)` 返回 task，`.done(res)` 里才是
`{ ok, booking, skipped }`；`.fail` 是落库失败。**写失败必须让用户看得见**——
客人不能看到「已提交」而什么都没落库，老板不能看到卡片变成「已确认」而云端没改。
内存里的乐观改动会自动回滚，但提示要页面自己给。

### 页面统一是「两段式」

三个有数据的页面（预约 / 订单 / 改价）都是同一个形状：

| | 干什么 | 取数吗 |
|---|---|---|
| `repaint()` | 把手上这份缓存画上屏 | **不取** |
| `refresh(cb)` | 取一次权威数据，**回来之后**再 repaint | 取 |
| `onShow()` | `this.repaint(); this.refresh();` | |

这么分是为了接云开发那天：数据在网络上，回来得晚。先 repaint，界面立刻有内容
（冷启动第一屏就靠这个），代价是第一屏可能旧一拍。

**凡是依赖最新占用情况的判断，都必须写在 `refresh` 的 `done` 里。** 现在有两处：
`pruneSel()`（把被订走的格子从选择里剔掉）和「今天已过完时跳到最近一个可约日期」。
写在 `core.refresh()` 的下一行，本地照样全绿、云端拿旧数据算。

这不是纸上谈兵，是实测出来的：把 `pruneSel()` 挪到 `done` 外面，只有**一条**断言变红
（`sel.size` 该 0 实际 1）。格子本身反而看不出来——`repaint` 读的是实时数据，会自己
纠正过来。所以线上会看到「格子已经变成『待』了，底栏却还算着它」，客人点提交才发现被剔掉。

订单页还有一条：下拉的转圈要在 `refresh(cb)` 的**回调里**才 `stopPullDownRefresh()`。
立刻停的话，云端转圈先消失、列表后刷新，老板看到的是「下拉了、没反应」。

`smoke.js` 里有一节专门测这个（`holdServer()`）：把「服务器」按住不返回，
先断言界面已经有内容、且**没有**提前剔选择；再放行，断言剔干净了。
整套测试里只有那一节能区分「取数前」和「取数后」——其余用例跑在同步后端上，
两个瞬间是同一个瞬间。

**测试全程是同步跑的**，靠的就是「本地后端同步回调」这条性质。
`smoke.js` 里有一条断言专门盯着它：谁把本地后端改成 `setTimeout` 式，
那条会立刻红在 exit 3，而不是让几百条断言悄悄变成假绿。

> **不要在这个项目里引入 `async` / `await` 或 Promise 来做这些事。**
> 测试跑在 macOS 自带的 `jsc` 上，未处理的 Promise 拒绝在那里是
> **静默 exit 0**——断言失败会变成「假装通过」。task 没有这个问题：
> 失败仍然是同步抛出，仍然是 exit 3。

有一套桩件替掉了 `Date` 和 `setTimeout`，让「现在是几点」和
「延迟的那一下什么时候执行」都变成测试里可以拨的旋钮。

改了 `core.js` 或页面逻辑后跑一下，比在模拟器里手点快得多。
尤其是价格和占用这两块——它们出问题时在界面上往往看不出来。

测试里有一组**可控时钟**的用例（`setClock(20, 15)`），
能把「现在是几点」拨到任意时刻再跑一遍，覆盖「晚上打开」
「今天已过完」这类只有特定时间才出现的场景。

## 九、关于原型

`prototype/` 是最早用来对需求的 HTML 原型，**已经停止维护**，
和现在的小程序对不上了（它还是半小时一格、还没有过期提示）。

留着是为了回头看当初的设计取舍。**改代码请只改 `miniprogram/`**，
别拿 `prototype/` 当参考——它不反映现在的行为。

不需要了可以直接删掉整个 `prototype/` 目录。
